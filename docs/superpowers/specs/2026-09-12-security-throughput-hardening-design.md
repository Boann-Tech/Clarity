# Security and Throughput Hardening — Design

**Date:** 2026-09-12
**Status:** Approved for planning
**Sub-project:** 2 of 4 in the Clarity hardening program (P0 security/ops). Follows pluggable LLM providers; precedes P1 product and P2 quality.

## Summary

Three P0 items from the defect-review triage: (1) eliminate the DNS-rebinding TOCTOU in the evidence fetcher by pinning each connection to a pre-validated public IP using a custom httpcore network backend; (2) make Python dependencies reproducible and auditable through hash-pinned pip-tools locks plus `pip-audit`/`npm audit` in CI; (3) stop claim-heavy pages from self-inflicting HTTP 429s by checking the response cache before consuming rate-limit units and adding a bounded batch endpoint that the extension uses instead of ten parallel requests.

## Goals

- Every outbound evidence fetch dials the exact IP that was validated, with TLS SNI and certificate verification still bound to the original hostname.
- Refuse unix sockets, non-global addresses, and mixed public/private DNS answers.
- `requirements.txt` and `requirements-dev.txt` become hash-pinned locks generated by `pip-compile`; Docker installs with `--require-hashes`; CI fails on known vulnerabilities in Python or npm dependencies.
- `/api/check` cache hits do not consume rate-limit units.
- A single batch request of up to 10 claims serves cache hits free, charges only uncached claims, and is processed with server-side bounded concurrency; the extension uses it with one timeout budget.
- `/api/check` remains fully compatible for existing callers.

## Non-goals

- Changing search providers, passage extraction, verdict logic, or the evidence-first invariant.
- A general-purpose proxy, allowlist management UI, or per-domain egress policy beyond the existing curated tiers.
- Dependency upgrade work or version bumps beyond pinning what is already in use.
- Streaming or partial batch responses; the batch call returns when all claims complete.
- Extension-side provider settings or any other provider work.

## 1. Pinned Egress Transport

New module `backend/app/egress.py`:

```python
class BlockedHostError(Exception): ...

async def resolve_public_ips(host: str) -> list[str]:
    """Resolve host once; require every address to be global; return all of them."""

class PublicOnlyBackend(httpcore.AsyncNetworkBackend):
    """Network backend that dials a pre-validated IP for every TCP connection."""
    async def connect_tcp(self, host, port, timeout=None, local_address=None, socket_options=None)
    async def connect_unix_socket(self, path, timeout=None, socket_options=None)  # always raises
    async def sleep(self, seconds)  # delegates

def build_pool() -> httpcore.AsyncConnectionPool:
    return httpcore.AsyncConnectionPool(network_backend=PublicOnlyBackend())
```

Behavior:

- `resolve_public_ips` uses `asyncio.get_running_loop().getaddrinfo(host, None)`; if there are no results, any address fails `ipaddress.ip_address(...).is_global`, or parsing fails, it raises `BlockedHostError`. Returning the validated list is safe because every address in the answer was checked.
- `PublicOnlyBackend.connect_tcp` resolves the host, then tries each validated address in order by calling the delegate `AnyIOBackend.connect_tcp(str(ip), port, ...)`; it raises `BlockedHostError` only when every address fails to connect. Passing literal IPs means the delegate cannot re-resolve a hostname, which is what closes the rebinding window. httpcore computes TLS `server_hostname` from the origin URL host independently of the dialled address, so SNI and certificate verification remain correct.
- `connect_unix_socket` raises `BlockedHostError` unconditionally, delegating the no-unix-socket policy to the transport.
- The delegate is `httpcore._backends.anyio.AnyIOBackend`, a private import. It is acceptable because `httpcore` becomes a direct, pinned dependency (`httpcore>=1.0,<2`) in this sub-project; the spec records the coupling so a future httpcore major bump re-verifies the backend API.

`backend/app/evidence.py` changes:

- `fetch_page` keeps its public contract (`FetchedPage | None`) and manual redirect loop, but each call builds its own pool via `build_pool()` and closes it with `await pool.aclose()` in a `finally`. It no longer imports `httpx` for fetching.
- A helper `_request(pool, url, headers, max_bytes)` performs one hop:

```python
async with pool.stream("GET", url, headers=headers) as response:
    status = response.status
    headers = {key.decode("latin-1").lower(): value.decode("latin-1") for key, value in response.headers}
    chunks = []
    total = 0
    async for chunk in response.aiter_stream():
        total += len(chunk)
        if total > max_bytes:
            return status, headers, None
        chunks.append(chunk)
```

- httpcore responses do not expose a final URL; the request URL is already the validated hop, so the helper returns only status/headers/body, and `fetch_page` tracks the current URL itself as it follows redirects manually.
- Existing pre-checks stay: `is_public_http_url` (scheme/host), `classify_domain(url).tier in CURATED_TIERS`, per-hop validation, browser-UA retry for 401/403/429, `text/html`/`text/plain` content-type check, byte caps scaled by tier.
- `host_is_public` moves to `egress.py` as `resolve_public_ip`'s validation core; `evidence.py` may keep a thin alias for tests until they migrate.

## 2. Locked Dependencies and Audits

- `backend/requirements.in`: top-level runtime dependencies — `fastapi`, `uvicorn[standard]`, `httpx`, `httpcore>=1.0,<2`, `pydantic`, `pydantic-settings`, `openai`, `defusedxml`.
- `backend/requirements.txt`: generated by `pip-compile --generate-hashes --output-file requirements.txt requirements.in`; fully pinned transitive versions with SHA-256 hashes and a header naming the generating command.
- `backend/requirements-dev.in`: `-r requirements.in` plus `pytest`, `pip-tools`, `pip-audit`; `requirements-dev.txt` compiled the same way.
- `backend/Dockerfile`: `pip install --no-cache-dir --require-hashes -r requirements.txt`.
- CI (`.github/workflows/test.yml`): backend job installs `requirements-dev.txt` with hashes, then runs `pip-audit -r requirements.txt` before tests; `pip-audit` failure fails the job. Extension job adds `npm audit --audit-level=high` before/after tests.
- Documented regeneration commands live in `README.md` (backend section): after editing a `.in` file, run the two `pip-compile` commands with Python 3.12.
- The lock files are the source of truth; `Dockerfile` and CI never install from `.in` files.

## 3. Cache-First Rate Limiting and Batch Endpoint

### Rate limiting

- `SlidingWindowLimiter` gains `async def allow_many(key, count, per_minute, per_hour) -> bool`: checks capacity for `count` events atomically under the lock, appends them on success, and never partially consumes on rejection.
- `main.py` stops declaring `_enforce_limits` as an endpoint dependency. Auth (`_require_token`) stays a dependency. Each endpoint performs, in order: validate → normalize → cache lookup → `allow_many` for the number of uncached claims → run.
- Cache hits consume zero units; rejected requests consume zero units.
- Defaults change: `CLARITY_RATE_LIMIT` 10 → 60 per minute, `CLARITY_RATE_LIMIT_HOUR` 50 → 500 per hour. `.env.example` and README document why (a first scan of a 10-claim page plus re-checks should not self-throttle).

### Pipeline extraction

`main.py` extracts the existing pipeline into:

```python
async def _check_normalized(
    req: CheckRequest,
    normalized_claim: str,
    llm_available: bool,
    request_id: str,
    now: str,
) -> CheckResponse
```

It contains the current steps (LLM normalization, retrieval loop, dedupe, verdict, boundary enforcement, citation formatting) and writes the result to `_response_cache`. `/api/check` keeps returning a single `CheckResponse` and is unchanged for clients.

### Batch endpoint

New models in `backend/app/models.py`:

```python
class BatchCheckRequest(BaseModel):
    claims: list[str] = Field(..., min_length=1, max_length=10)
    # each claim validated with the same whitespace normalize + 10..500 rules as CheckRequest

class BatchCheckResponse(BaseModel):
    request_id: str
    results: list[CheckResponse]
```

`POST /api/check/batch`:

1. Requires the same optional bearer token as `/api/check`.
2. Validates every claim up front; 422 on any violation.
3. For each claim, normalizes and checks `_response_cache`; cached claims produce their stored response.
4. Charges `allow_many(client, count=uncached_count)`; 429 when over budget.
5. Runs uncached claims with `asyncio.gather` behind a semaphore of 3, preserving input order in `results`.
6. Pipeline failures are not swallowed per claim: the request fails as a whole (500), consistent with `/api/check`.

### Extension

- `src/shared/protocol.ts` gains:

```ts
export interface BatchCheckResponse {
  results: Array<{ claim?: string; assessment?: { verdict?: string; confidence?: number; explanation?: string }; citations?: Array<Record<string, unknown>>; checked_at?: string }>
}

export async function fetchBatchAssessments(
  claims: string[],
  settings: AppSettings,
  fetchFn: typeof fetch = fetch,
): Promise<BatchCheckResponse | { error: string } | null>
```

It posts `{ claims }` to `${normalizedBackendUrl}/api/check/batch` with the auth header when a token is set and a 120 s `AbortSignal.timeout`, returning batch results, an `{ error }` marker for non-ok responses, or `null` for network failure.

- `worker.ts` `handlePageCheck`:
  - Selects up to `maxClaims` checkable claims.
  - Filters out claims already in the in-memory cache (returning those immediately).
  - Sends the remaining claims as one `fetchBatchAssessments` call.
  - Maps each raw result through `assessmentFromResponse`, caches each `ClaimCheck`, and preserves input order.
  - On `{ error }` or `null`, produces one unverified/offline `ClaimCheck` per pending claim (same explanation strings as today).

## Data Flow

1. Extension extracts claims → filters its cache → one batch POST.
2. Backend token check → per-claim validation → cache lookup → charge uncached count → bounded concurrent pipeline → `results` in order.
3. Each claim's pipeline fetches pages through `PublicOnlyBackend`, which resolves once and dials the validated IP; redirect hops repeat validation.
4. Extension maps, caches, and renders results; history is written once as today.

## Error Handling

- `BlockedHostError` and any httpcore exception inside `fetch_page` return `None` (source dropped), exactly as today's fetch failures.
- Batch validation errors return 422 with FastAPI's standard detail; token errors 401; rate limit 429. No partial batch responses; a batch is all-or-nothing.
- Missing/invalid lock files fail Docker build and CI installs loudly (`--require-hashes`).
- Audit failures fail CI; they never affect runtime behavior.
- Pinned-IP failures (DNS returns no global address) are source-level failures, not request failures; other sources still contribute.

## Testing

- `backend/tests/test_api_ops.py`: cache hits do not consume limits; rejected requests do not consume; `allow_many` atomicity (partial rejection leaves no events).
- New `backend/tests/test_api_batch.py`: order preservation; cache hits free; per-uncached-claim charging; 429 when over budget; 422 for >10 or invalid claims; 401 without token; results equal single-endpoint results for the same claims.
- `src/shared/settings.test.ts` (or a new `batch.test.ts`): `fetchBatchAssessments` uses the injected fetch with the right URL, body, auth header, and timeout; maps non-ok to `{ error }` and thrown fetch to `null`.
- Full suites stay green: `python3 -m pytest -q`, `npm test`, `npm run build`.

## Security Notes

- The pinned connection removes the TOCTOU the previous README documented; the README residual note is updated to describe the pinning and its remaining limits (no IP allowlist beyond global-scope, private-DNS answers rejected).
- The AnyIO delegate import is private httpcore API; the direct `httpcore>=1.0,<2` pin bounds the exposure, and `test_egress.py` fails loudly if the backend contract changes.
- Hash-pinned installs remove version-substitution risk in Docker/CI.
- Batch endpoint keeps the same optional bearer token; it does not widen the trust boundary (same validation per claim, same rate accounting).

## Compatibility and Rollout

- `/api/check` request/response shape is unchanged; only cache-hit accounting and default rate limits change (documented in `.env.example`/README).
- Extension and backend deploy together for batch support; an old extension against a new backend keeps working via `/api/check`. A new extension against an old backend gets 404 for the batch route and reports `The Clarity backend rejected the request (HTTP 404)` per claim — degraded but not fabricated, and noted in the README.
- No database or persisted-format changes.

## Out of Scope

Client-visible provider work, search-provider changes, verdict logic, retry backoff for individual claims, site CI, observability, and the P1/P2 items.
